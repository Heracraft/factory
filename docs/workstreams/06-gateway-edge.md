# 06. gateway-edge

## 1. Goal

The edge is the one public entry point to tenant environments: an SSH
gateway that authenticates a user's certificate and relays them into their
guest, and the WireGuard hub every host dials so the gateway can reach
guests without hosts having any inbound exposure. It is a NixOS appliance
deployed with `nixos-rebuild`, not a Coolify container, because it needs raw
TCP and UDP ports and the kernel's WireGuard.

## 2. Scope: builds

- `nix/edge/`: a NixOS configuration for the edge VM: WireGuard hub
  (`wg0`), the `gateway` systemd service, nftables, sshd for operators on
  a non-22 port, Fluent Bit, node_exporter, automatic security updates
  disabled in favour of platform-driven rebuilds.
- `cmd/gateway` and `internal/gateway/`: the Go SSH gateway per
  `interfaces/ssh-gateway.md`: server with a host certificate, certificate
  authentication against the User CA, revocation cache, route lookup via
  the api, a second SSH client session to the guest authenticated with a
  gateway-issued 5-minute certificate, channel and request relay, session
  reporting, metrics.
- WireGuard peer management: a small `wgsync` loop in the gateway binary
  (`gateway wgsync`) that reads the host list from the api
  (`/internal/hosts`, added to `api.md` by this workstream as I-4) and
  applies peers with `wg set` without restarting the interface.
- The hook ingest and noVNC relay listeners that guests reach over
  WireGuard (`:8443` and `:6081` on the edge's wg address). Hook ingest is
  a thin HTTPS forwarder to the api's `/internal/events` (I-4 adds it);
  noVNC relay is a TCP proxy that the CLI's `open --desktop` reaches through
  an SSH forward, so it is a plain port relay to `guest_ip:6080` keyed by
  the SSH session's project.
- A stub for the HTTPS preview proxy: the listener on 443 exists, serves a
  static "previews are not enabled yet" page, and the code path that would
  route `<port>-<slug>.factory.herakraft.co` is laid out with the
  authentication cookie check as a documented function that returns
  `not implemented` until `features/ports-and-previews.md` is built.

## 3. Scope: does not build

- The SSH CA, certificate issuance, revocation storage, route resolution
  logic: workstream 05 (the gateway calls `/internal/*`).
- Host-side WireGuard client configuration: workstream 01 (it consumes the
  keys hostd received at registration).
- The CLI's SSH config writing and certificate refresh: workstream 07.
- Guest sshd configuration: workstream 02.
- Provisioning the edge VM, its public IP, DNS records, and the NSG:
  workstream 11. This workstream provides the NixOS configuration 11
  deploys.
- The preview proxy's real behaviour: later, per `features/ports-and-previews.md`.

## 4. Interfaces owned / consumed

Owned: the relay side of `interfaces/ssh-gateway.md`; the edge's WireGuard
address plan (`10.255.0.0/16` for hosts, `10.255.0.1` for the edge);
`/internal/hosts` and `/internal/events` additions to `api.md` (I-4).

Consumed: `/internal/route`, `/internal/revoked`, `/internal/ca`,
`/internal/sessions` (05); `interfaces/host-conventions.md` for the guest
address space; `interfaces/guest-conventions.md` for the noVNC port.

Fake: tests use `internal/fakes/api` and `internal/ca/testca`, plus an
in-process `ssh.NewServer` standing in for a guest sshd.

## 5. Design detail

### 5.1 The edge VM

`nix/edge/configuration.nix`:

- `networking.wireguard.interfaces.wg0`: private key from
  `/var/lib/factory/edge/wg.key` (generated by `factory-admin edge init`
  and placed by workstream 11's deploy), listen port 51820, address
  `10.255.0.1/16`, no static peers; peers are managed at runtime by
  `wgsync`. `ip_forward = 1`. Routes for each host's guest `/22` are added
  by `wgsync` with `ip route add <cidr> dev wg0`.
- nftables: input allows 22 (gateway), 443 (preview stub), 51820/udp,
  2222 (operator sshd, key-only, restricted to the wg network and a
  documented operator IP list), 9100 and 9102 from wg only (node_exporter,
  gateway metrics). Forward allows wg0 to wg0 only for the gateway's own
  connections (the edge originates them, so `ct state established` plus
  output rules suffice; hosts never route through the edge to each
  other, and that is enforced by `AllowedIPs` being per-host).
- `systemd.services.gateway`: `DynamicUser`, `AmbientCapabilities =
  CAP_NET_BIND_SERVICE`, `StateDirectory = factory/gateway`, environment
  `API_URL`, `GATEWAY_CLIENT_CERT/KEY` paths, `HOST_KEY` and `HOST_CERT`
  paths, `USER_CA_PUB` fetched at start from `/internal/ca` and refreshed
  hourly. `Restart = always`, `RestartSec = 1`.
- `systemd.services.wgsync`: runs `gateway wgsync` with
  `CAP_NET_ADMIN`, every 30 s.
- Operators' sshd on 2222 trusts the Host CA for user certificates minted
  by `factory-admin ca sign-client --operator`.
- Fluent Bit ships journald to Loki with `host = edge`.
- The VM is a `Standard_D2s_v5` (Intel is not needed here; it is chosen for
  consistency and 2 vCPU handle a few hundred relays); public IP is static.

### 5.2 Gateway: accepting the client

`internal/gateway/server.go` uses `golang.org/x/crypto/ssh`:

- `ServerConfig.PublicKeyCallback` accepts only certificates
  (`*ssh.Certificate`, type user cert). `ssh.CertChecker` with
  `IsUserAuthority` checking the key equals the User CA public key,
  `IsRevoked` consulting the revocation cache (a `map[uint64]struct{}`
  refreshed every 30 s from `/internal/revoked?since=<last>`), and
  `UserKeyFallback` nil, so plain keys are refused with `permission denied
  (certificate required)`.
- The login name `conn.User()` is split on the last `.` into slug and
  handle. The user name only arrives with the auth request, after key
  exchange, so a malformed name is an auth failure with the banner `login
  name must be <project>.<user>`; `BannerCallback` returns the message so
  OpenSSH clients print it.
- After the certificate verifies, `PublicKeyCallback` calls
  `/internal/route?login=` (cached 5 s per login) and checks the
  certificate's `ValidPrincipals` contains the returned `project_id`.
  Mismatch: `certificate not valid for this project`. State not `running`:
  `<slug> is stopped; run \`factory start\``. The route (guest ip,
  project id) is stored in `Permissions.Extensions` for the connection.
- Host key: `ssh.NewCertSigner(hostCert, hostKey)`.
- Limits: 4 concurrent auth attempts per source IP, 200 concurrent
  connections total, 30 s auth timeout, `MaxAuthTries 3`.

### 5.3 Gateway: dialing the guest

For each accepted connection, `relay.go` opens an SSH client to
`guest_ip:22` over the wg interface:

- Auth: a certificate signed on the fly. The gateway holds its own ed25519
  key pair; it asks the api for a certificate for that key with principal
  `project_id`, 5-minute validity, `key_id = "<user>:<handle>:via-gateway"`
  via `POST /internal/gateway-certs` (I-4). Certificates are cached per
  project for 4 minutes so a burst of connections does not hit the api
  per connection. Falling back to the client's forwarded agent is not
  implemented in the first release; the gateway certificate path is the
  only one, which keeps the guest's sshd check uniform.
- Host key verification of the guest: `ssh.CertChecker.CheckHostKey`
  against the Host CA with the guest's `guest_ip` as the expected
  principal.
- Timeouts: 10 s dial, and the connection fails with `environment is not
  accepting connections yet` if sshd is not up, which the CLI turns into
  a retry loop for 60 s after a `start`.

### 5.4 Relay semantics

After both sides exist, the gateway relays:

- New channels from the client (`session`, `direct-tcpip`) are opened on
  the guest side with the same type and extra data; the two channels are
  piped both ways with `io.Copy` and stderr piped for `session`. Channel
  requests (`pty-req`, `env`, `shell`, `exec`, `subsystem`,
  `window-change`, `signal`, `exit-status`, `exit-signal`,
  `auth-agent-req@openssh.com`) are forwarded in both directions with
  `WantReply` honoured.
- `env` requests are filtered to a safe list (`TERM`, `LANG`, `LC_*`,
  `COLORTERM`, `TZ`), because sshd's `AcceptEnv` in the guest is the real
  guard and the filter just avoids noise.
- Global requests: `tcpip-forward` (remote forwards, `-R`) are forwarded
  to the guest, and the guest's resulting `forwarded-tcpip` channels are
  relayed back. `keepalive@openssh.com` is answered locally and also sent
  to the guest every 30 s so both halves notice a dead peer.
- Agent forwarding: `auth-agent-req@openssh.com` on a session is forwarded
  and the guest's `auth-agent@openssh.com` channel requests are relayed
  back to the client, so `git push` over SSH inside the guest can use the
  laptop's agent while attached.
- Close handling: when either side closes, the other is closed after
  pending data flushes; exit status is delivered before close.

The relay is per-connection goroutines with a context that cancels on
either side's close, and a hard cap of 24 hours per connection (tmux keeps
the session; the CLI reconnects).

### 5.5 Session reporting and metrics

On accept: `POST /internal/sessions {project_id, opened, cert_serial}`; on
close, `closed`. Fire-and-forget with one retry; a failure is a log line,
not a refusal.

Metrics `factory_gateway_`: `connections_open`, `auth_total{result}` with
results `ok`, `no_cert`, `bad_ca`, `revoked`, `expired`,
`wrong_principal`, `stopped`, `route_error`, `rate_limited`;
`relay_bytes_total{direction}`; `dial_errors_total`; `session_seconds`
histogram; `revocation_cache_age_seconds`; `wgsync_peers`;
`wgsync_errors_total`.

Logs: one line per connection open and close with `project_id`,
`cert_serial`, `source_ip` truncated to /24 for IPv4 and /48 for IPv6,
duration, bytes; auth failures with `result` and the truncated source.
Never the login name's handle in plain text beside the source address
beyond what the project id already implies; never channel contents.

### 5.6 wgsync

Every 30 s: `GET /internal/hosts` returns `[{host_id, wg_pubkey, wg_ip,
guest_cidr, state}]`. For each host not `retired`: `wg set wg0 peer
<pubkey> allowed-ips <wg_ip>/32,<guest_cidr> persistent-keepalive 25`, and
`ip route replace <guest_cidr> dev wg0`. Peers present on the interface but
absent from the list are removed. Idempotent; diffs are logged.

### 5.7 Hook ingest and noVNC relay

`:8443` on `10.255.0.1`: HTTPS with the edge's internal certificate;
accepts `POST /hooks` from guest addresses only (nftables limits the
source to `10.64.0.0/12`), forwards the JSON to the api's
`/internal/events` with the source guest ip added so the api can map it to
a project. Body cap 4 KB, 10 requests per second per source.

Guests therefore have two ways to raise an event: guestd over vsock
(primary) and this HTTP path (used only when guestd is unavailable, for
example by a hook fired during a guestd restart). Both land in the same
`events` table with the same dedupe key (`project_id, agent, kind, ts
rounded to the second`).

`:6081` is not a general relay; `factory open --desktop` uses a normal SSH
`-L 6080:localhost:6080` through the gateway relay, so no separate noVNC
listener is needed. The port is reserved and the listener is not built.
Recorded here so nobody adds it.

### 5.8 Preview proxy stub

`:443` serves a static page and `/healthz`. `internal/gateway/preview/`
contains `Route(host string) (project, port, error)` parsing
`<port>-<slug>-<handle>.factory.herakraft.co` (handle included because
slugs are per user), `Authenticate(r *http.Request) (userID, error)`
returning `not implemented`, and a reverse proxy skeleton. The wildcard
certificate is provisioned by workstream 11 with DNS validation and placed
at `/var/lib/factory/edge/tls/`; the stub serves it so the certificate
pipeline is proven before the feature exists.

## 6. Failure modes

| Failure | Behaviour | Visible outcome |
|---|---|---|
| api unreachable | auth continues with the cached CA and revocation list up to 1 h old; route lookups fail after cache expiry | client: `gateway cannot reach control plane; try again shortly`; alert `gateway_api_unreachable` |
| Revocation cache stale past 1 h | new connections refused, existing continue | client: same message; alert |
| Guest sshd not up | `environment is not accepting connections yet` | CLI retries 60 s after a start |
| WireGuard peer missing for a host | dial to its guests fails with `no route to host` | alert on `dial_errors_total` for a host; `wgsync` log shows the diff |
| Certificate expired | `permission denied (certificate expired)` | CLI refreshes and retries once automatically |
| Wrong principal | `certificate not valid for this project` | CLI re-requests a cert including the project |
| Connection cap reached | refuse with `gateway busy` | alert at 80 percent |
| Gateway restart (deploy) | every relay drops; tmux sessions in guests persist | CLI reconnects on the next `attach`; a banner on reconnect says `reconnected` |
| Malformed login name | banner and auth failure | user sees the banner |
| Source IP auth flood | 4 concurrent attempts then `rate_limited` | metric |

## 7. Testing

- Unit: login name parsing, principal check, revocation cache diffing,
  `env` filter, wgsync diff against a fake `wg show` output, preview host
  parsing.
- Integration in-process: `testca` mints a User CA and Host CA; an
  in-process guest `ssh.ServerConfig` trusting the CA; the gateway in
  front; a real `ssh` client (`golang.org/x/crypto/ssh` client and also
  the OpenSSH binary in CI) runs `echo`, a pty shell with a window change,
  `-L` and `-R` forwards, agent forwarding with a test agent, and an exit
  status of 3. Assertions on bytes and requests seen by the fake guest.
- Failure paths in section 6 each have a test that asserts the exact
  banner or error string.
- On the staging edge: an OpenSSH client from a laptop through the real
  WireGuard to a real guest on the M1 host, including VS Code Remote-SSH
  attaching with the CLI-written config.
- Soak: 100 connections held 1 hour with `yes | head -c 1G` relayed; no
  goroutine leak (`/debug/pprof/goroutine` count returns to baseline).

## 8. Rollback

`nixos-rebuild switch --rollback` on the edge restores the previous gateway
binary and configuration in seconds; relays drop once. WireGuard peer state
is rebuilt by `wgsync` within 30 s of any version. No persistent state
except keys and certificates, which are not changed by deploys.
